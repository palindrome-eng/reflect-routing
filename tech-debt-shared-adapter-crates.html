Tech debt: extract shared titan/<product> and jupiter/<product> adapter crates

Filed 2026-07-07 after implementing titan/whitelabel + jupiter/whitelabel, the third instance of a pattern first noticed in bonds (the second). Scoped out, not implemented - repo: ~/projects/reflect/reflect-routing.

Status: not started. This is a deferred refactor of already-committed, already-pushed code (titan/lending, titan/bonds, jupiter/lending, jupiter/bonds all ship on origin/feat/refactor-routing-based-on-reflect-core-sdk). Do not start it opportunistically inside an unrelated change - it touches every existing adapter crate's imports. Do it as its own PR.

1. The problem, with numbers

Every new titan/<product> and jupiter/<product> crate is built by copying the previous product's crate and swapping the venue type. That copy carries along a large block of code that is byte-identical across all three existing instances (lending, bonds, whitelabel) and will be byte-identical again for the fourth (rlp, not yet built). None of this is Reflect-specific - it is the vendored upstream interface (Titan's TradingVenue trait, Jupiter's Amm trait) that this workspace copies per-crate instead of depending on, for reasons that remain valid (see §4) but that don't require the copy to happen more than once.

1.2 Jupiter: ~150-180 lines of trait/type boilerplate + a ~110-line enum, ×3 crates

jupiter/{lending,bonds,whitelabel}/src/lib.rs are 300 / 319 / 315 lines each. diff jupiter/lending/src/lib.rs jupiter/bonds/src/lib.rs shows the first ~146 lines (module doc aside) - the vendored Amm trait, SwapMode, QuoteParams, Quote, QuoteMintToReferrer/AccountMap type aliases, SwapParams, SwapAndAccountMetas, KeyedAccount, AmmContext, and the whole ClockRef struct + its two impls - are identical. Only the module doc, the venue import, and the ReflectXAmm struct/impl (from line ~150 on) differ.

swap.rs is the same shape: a ~110-line vendored Swap enum (the full upstream tag list - Saber, TokenSwap, Raydium, ... TesseraV, ReflectS1) is identical across all three crates. Only the handful of appended Reflect-specific tags differ:

lending:    (nothing appended - ReflectS1 is the whole Reflect surface)
bonds:      + ReflectBondsMint, ReflectBondsSwap, ReflectBondsRedeem
whitelabel: + ReflectProxyWrap, ReflectProxyUnwrap

This is actually a correctness smell, not just a size one: there are currently three distinct Swap types (reflect_jupiter_lending::Swap, reflect_jupiter_bonds::Swap, reflect_jupiter_whitelabel::Swap) that are not interchangeable even though conceptually there is exactly one Jupiter backend tag space. Nothing forces that today, but it's the kind of thing that bites later (e.g. a router or test harness that wants to reason about "all Reflect tags" has to know about N unrelated enums).

2. Proposed design

Two new workspace-internal crates, one per aggregator, holding exactly the vendored boilerplate and nothing product-specific:

titan/common/                          # pkg reflect-titan-common
  Cargo.toml
  src/
    lib.rs                             # pub mod trading_venue; pub mod account_caching;
    trading_venue/
      mod.rs                           # moved verbatim from titan/lending
      bounds.rs                        # moved verbatim
      error.rs                         # moved verbatim
      token_info.rs                    # moved verbatim
      # NOTE: protocol.rs does NOT move - stays per-product (see 2.1)
    account_caching/
      mod.rs                           # moved verbatim

jupiter/common/                        # pkg reflect-jupiter-common
  Cargo.toml
  src/
    lib.rs                             # Amm trait, ClockRef, QuoteParams/Quote/SwapParams/
                                        #  SwapAndAccountMetas/KeyedAccount/AmmContext, AccountMap alias
    swap.rs                            # the vendored tag enum, now holding EVERY product's
                                        #  Reflect tags in one place (see 2.2)

2.1 Titan: why protocol.rs stays behind

PoolProtocol is a plain enum with one variant per product (ReflectLending, ReflectBonds, ReflectWhitelabel, ...). Sharing it would mean either (a) one enum in the common crate that every product crate adds a variant to - which reintroduces a dependency edge in the wrong direction (the shared crate would need to know about every product), or (b) a generic/trait-object protocol() return type, which is more machinery than a 30-line file justifies. Leave it per-crate; it is the one piece of vendored-shaped code that is genuinely product-specific, and it's small enough that copying it is cheaper than any abstraction over it.

2.2 Jupiter: unify the Swap enum instead of forking it

Move the vendored ~110-line enum into jupiter/common::swap and append every product's Reflect tags to that single definition:

pub enum Swap {
    // ...the ~65 vendored upstream variants, unchanged...
    ReflectS1,               // lending
    ReflectBondsMint,        // bonds
    ReflectBondsSwap,
    ReflectBondsRedeem,
    ReflectProxyWrap,        // whitelabel
    ReflectProxyUnwrap,
    // future: ReflectRlpRestake, ReflectRlpSwap, ...
}

Each jupiter/<product> crate imports this one type instead of defining its own. Adding a fifth product means adding variants to one file in one place, not forking a ~110-line enum into a sixth copy. This also fixes the "three unrelated Swap types" smell from §1.2 - there is exactly one Jupiter tag space, so there should be exactly one Rust type for it.

2.3 What stays per-crate (unchanged)

CrateStays local
titan/<product>trading_venue/protocol.rs (one enum variant); src/reflect.rs (the whole adapter - ReflectXVenue, FromAccount, TradingVenue, AddressLookupTableTrait impls); src/lib.rs (now trivial: pub mod reflect; pub use reflect::ReflectXVenue; plus a pub use reflect_titan_common::{trading_venue, account_caching}; re-export so downstream code's crate::trading_venue::... paths keep working, or callers switch to importing from reflect_titan_common directly)
jupiter/<product>ReflectXAmm struct + its Amm impl (the only genuinely product-specific code); its own Swap tag additions live in the shared crate's swap.rs, but which tags a given product's get_swap_and_account_metas emits is still 100% local logic

No change to the Reflect-side venue design (LendingVenue/BondVenue/WhitelabelVenue in core/) - this refactor is scoped strictly to the vendored third-party interface layer. It does not reopen or relitigate the earlier, separate decision to keep those venues concrete with no shared trait (that decision is about Reflect's own abstraction; this one is about not re-typing someone else's interface by hand three times).

3. Migration plan

  1. Create titan/common: git mv titan/lending/src/trading_venue titan/common/src/trading_venue minus protocol.rs (copy that one back into each product crate first, unmodified), same for account_caching. Add the crate to the workspace glob (already covered by members = [..., "titan/*"] if placed under titan/, or add it explicitly if it should sit outside that glob).
  2. Update titan/lending, titan/bonds, titan/whitelabel Cargo.tomls to depend on reflect-titan-common; delete their local trading_venue/{mod,bounds,error,token_info}.rs and account_caching/mod.rs; update src/lib.rs and src/reflect.rs imports (crate::trading_venue::* → reflect_titan_common::trading_venue::*, same for account_caching).
  3. Create jupiter/common the same way: move the shared prefix of lib.rs (through the ClockRef impls) and all of swap.rs except the trailing product tags, which get consolidated into the single enum per §2.2.
  4. Update jupiter/lending, jupiter/bonds, jupiter/whitelabel Cargo.tomls to depend on reflect-jupiter-common; each crate's lib.rs shrinks to imports + its ReflectXAmm definition; delete the local swap.rs files (or reduce to a one-line re-export if any product wants to keep a local Swap alias for doc-friendliness).
  5. Verify: cargo build/test/clippy/fmt --workspace, then re-run the LiteSVM parity suites (titan/lending's Kamino-backed suite, titan/bonds', titan/whitelabel's live-mainnet-.so suite) to confirm the import churn didn't silently change behavior. These are pure moves - no logic changes - so a green re-run is the whole verification bar.
  6. rlp lands on top of the shared crates from day one - no fifth copy of the vendored files.

4. Why the vendoring exists at all (context, not up for debate here)

Both vendoring decisions are locked and this refactor does not touch them:

  • Jupiter: jupiter-amm-interface v0.6.1 pulls solana 3.x/4.x split crates, ABI-incompatible with the solana 2.2 Pubkey/Instruction `reflect-sdk` is built on. The Amm trait + Swap enum are hand-copied to stay on 2.2. ponytail: drop the vendored copy and depend on the real crate once it ships a 2.2-compatible release (noted in every swap.rs module doc today).
  • Titan: the TradingVenue trait is vendored from Titan-Pathfinder/integration-template because there is no published crate to depend on at all - the framework supplies its own AccountsCache, so the upstream RPC-backed cache helper is deliberately omitted too.

This ticket is only about where the one-time copy lives - one shared internal crate vs. N per-product copies - not about removing the vendoring itself.

6. Out of scope / explicitly not doing

  • Not touching core/ (the concrete LendingVenue/BondVenue/WhitelabelVenue venues) - separate, already-settled decision.
